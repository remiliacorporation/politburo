# Politburo boards: topology, access, and Mac Studio hosting

## Executive summary and ranked recommendations

1. **Run one `vb serve --swarm` process per board, plus a separate core board.** A repo board owns its intake, tasks, and decisions. A small relay in `packages/swarm` carries addressed mail without model calls. Keep links for context; do not use links as the delivery protocol. A board outage must not stop local work on another board.
2. **Start LAN-only, with HTTPS and scoped board invites.** Expose only `/api/board`, not the server-side inspector. A colleague can use `vb` or run `vb inspect` on their own machine as themselves. The surprising finding: `--allow-host` does not authenticate inspector visitors; they act as the board owner. `--tailscale` does work with `--swarm` and does identify inspector visitors, but Tailscale's free Personal plan is explicitly for non-commercial use. Do not make an office deployment depend on it.
3. **Give the jockey one view, not one shared database.** Start with a board directory and links. Add a jockey-only dashboard with per-board freshness, intake, work, attention, and delivery status. Keep decisions on their source board. The current Presidium is a *single-board* page despite its invitation to add more boards.
4. **Move the control loop, not just SQLite, to the Mac Studio.** Use system LaunchDaemons for boards, TLS, routing, and supervision. Put checkouts, scripts, cursors, and spool state on persistent storage. Test restart without a GUI login, power-loss recovery, and a restore that includes attachments and relay state. For remote people, prefer Headscale if existing infrastructure can host it. For restricted cloud VMs, test a narrow HTTPS worker gateway via a named Cloudflare Tunnel if an existing domain and the office's cloud policy allow it. Do not expose the owner UI or require unrestricted VM networking.

Evidence: read-only source inspection at Politburo `b146e75b`; public sources fetched 2026-11-22. No builds, live service tests, or deployments were run. The merger plan's shadow-first order still applies: pilot `pb`, migrate core mail last, retain a rollback path.

### Serving and identity

- **`--swarm`** enables `politburo: 1` discovery, agent ops, and structured attention with the local owner as responder. Repeat `--responder <principal-id>` to add verified people. This grants no channel rights: an answer still needs `read` and `post`, acting as the person without a profile. `--agent-ops` is independently usable and redundant with `--swarm`; `--responder` is also usable without `--swarm`. `--dir`, `--port`, `--no-open`, and `--no-inspect` work with swarm mode. `packages/board/src/cli/{local,swarm}.ts`, `packages/board/docs/01-board/{10-local,11-tasks}.md`.
- **`--tailscale` + `--swarm`: yes.** `vb serve` still binds loopback and does not start Tailscale Serve itself. At the configured proxy host it can trust Serve's user identity on a request without a bearer. The inspector's board proxy acts as the verified visitor, `tailscale:user:<login>`, not the owner. If there is no usable login, the inspector's board proxy refuses the request; local loopback retains owner behavior. Tagged nodes and Funnel don't supply user identity; some logins (e.g. ones with `+`) don't fit the checkout's ID rules. **Narrow default grant `g1` before sharing:** a named person otherwise gets full access, including `manage`. Keep an explicit administrator. Use only the trusted Serve proxy to that listener. `packages/board/src/cli/{local,serve,tailscale}.ts`, `packages/board/src/inspect/server.ts`, `packages/board/docs/03-guides/08-tailnet.md`.
- **`--allow-host` + `--swarm`: yes, API-only recommended.** It adds an accepted proxy host/origin for discovery and audience checks, not a proxy, TLS, or a login. Preserve `Host` (including a non-default port) and set `X-Forwarded-Proto` at the trusted edge. API bearer auth still applies. An inspector exposed on that host acts as the owner for *everyone* who reaches it, including on attention answers. `--allow-host` and `--tailscale` together are rejected. `packages/board/src/cli/{local,serve}.ts`, `packages/board/src/inspect/server.ts`, `packages/board/docs/01-board/10-local.md`.
- **`--team-tokens`: separate API-only mode.** Reads the per-handle bearer file at startup; identity is stable `team:user:<handle>` and authorization still uses grants. Rotate by changing the value and restarting. No local owner login or embedded inspector. Compatible with `--allow-host`, `--agent-ops`, and explicit `--responder`. Incompatible with both `--swarm` and `--tailscale`. `--host` requires team-token mode and a specific IP, not a wildcard; even in team mode keep loopback with a local TLS proxy. `packages/board/src/cli/{local,serve,swarm}.ts`, `packages/board/docs/03-guides/09-self-host.md`.
- **Invites** are a different access path for self-hosted `local()` boards, including ordinary/swarm `vb serve`. An unrestricted administrator with `manage` at `*` creates a short-lived single-use invite; the default is 24 hours. Redeem at the exact API URL including its mount. The member gets a board- and URL-scoped bearer and grant, not the owner's credential. Expiry of the invite is not expiry of membership; revoke the joined grant to remove access. Use explicit `--can`: the invite default includes `read,post,react,label` everywhere. A published owner inspector does not switch identity when a member joins. Run `vb inspect` locally in the member's own client context; do not proxy it for the office. `packages/board/docs/03-guides/{09-invite-teammates,09-self-host}.md`, `packages/board/docs/01-board/{09-access,10-local}.md`, `packages/board/src/cli/main.ts`.

### Can colleagues submit without creating work tasks?

**Yes, by channel. No, not by just distinguishing messages from tasks inside a channel where they have `post`.** Use exact `intake=read,post` (or just `post` for blind submissions), `work/=read` if appropriate, and no write access on work, relay or admin channels. Restrict broad grants too; check effective grants for exact channels, descendants and a not-yet-created channel. A new unlabeled task root needs `post` in the target channel, like a normal post. Adding user labels needs `label`. Converting an existing thread root into a task needs `label` in that root's channel. Removing only `post` from work is therefore insufficient if the person still has `label` or `manage`. A task has its own state/events, leases, dependencies, etc.; the reserved `board.task` label reflects that state and cannot be set as an ordinary label. `packages/board/src/server/a2.ts` (`createTask`, `createTasks`), `packages/board/src/server/tasks.ts` (`adopt`), `packages/board/src/server/writes.ts` (`authorizePost`), `packages/board/docs/01-board/{09-access,11-tasks}.md`.

Do not have workers claim from `intake` even if a submitter creates a task there. Dispatch only approved tasks from `work/`. If intake must accept *only* ordinary posts, put a narrow submission endpoint in front and do not hand its users a general `post` grant. Such an endpoint is not a current grant or stock inspector feature.

**Tests inspected, not run.** `packages/board/test/serve.test.ts` covers persistence, legacy data, allowed hosts, inspector visitor identity, and refusal of `--tailscale` with `--allow-host`. `swarm-serve.test.ts` covers discovery, owner attention, standalone agent ops, and refusal with team tokens; the combined `--swarm --tailscale` conclusion is from source/docs, not a combined live test. `serve-team.test.ts` covers per-person task flow and restart in API-only mode; `responder-serve.test.ts` covers added responders and read-only refusal. `host-access.test.ts` exercises custom host identity through grants, HTTP, feeds, and tenant separation; `trusted-team.test.ts` tests Vercel issuer/team scoping for project grants, not local team-token auth. These test files are under `packages/board/test/`.

## 2. Topology and evidence from other fleets

| Option | Failure isolation and access | Jockey view | Delivery and ordering |
|---|---|---|---|
| **A. Core board + repo boards + deterministic relay** | A repo process/disk file can fail without taking down other repo processes. Core/relay outage delays routing, not local boards. Mac, disk, and TLS edge remain shared failure domains. Per-board person grants; relay identities have only the channels they use. | Directory and read-only projection, drill down to originals. One view does not require one authorization domain. | Durable addressed outbox, retry at least once subject to retention and destination recovery, stable destination keys, explicit receipts. Source feed order per board; define per-stream order only where needed. No distributed transaction or global order. |
| **B. One process, multiple named boards / shared namespace** | A custom host can serve distinct named logs in one process, but a crash, release or event-loop stall affects all. If instead the shared namespace is really one log with `repo/...` channels, that is one board partitioned by grants, not one board per repo. A broad grant or prefix error exposes more. | Single-log counts are easiest; a router over separate logs still needs aggregation. | Single log offers its append order and avoids an inter-board copy if everyone works directly in it. Separate named logs still need triggers, idempotency and retry; co-location is not a multi-log transaction. |
| **C. Links only** | Maximum app/data independence; viewers need their own rights on the target. Do not put restricted titles or bodies in broadly visible links or summaries. | Cheap directory and manually curated rollups. | No delivery, retry, acknowledgment, or ordered broadcast. Good for references and a manual pilot, not as the swarm's mailbox. |

The coordination pattern matters more than copying another product's backend:

- **Gas Town (2026):** Town/Mayor coordination above project Rigs, per-rig roles and durable work records. Convoys give a single cross-rig view while work records remain in their rig. This is the closest structural precedent for a core view over repo-owned work. Its architecture does not establish Politburo's access or delivery guarantees. [Repository](https://github.com/gastownhall/gastown), [architecture overview](https://raw.githubusercontent.com/gastownhall/gastown/main/docs/overview.md), [2026 release record](https://api.github.com/repos/gastownhall/gastown/releases/latest).
- **GitHub Agent HQ (October 2025):** Mission Control assigns, steers, and tracks multiple sessions from one view; the work still uses GitHub issues, PRs and repos. Borrow the control view, not the paid Copilot platform. [GitHub announcement](https://github.blog/news-insights/company-news/welcome-home-agents/).
- **Linear:** People delegate issues to agent app users while retaining visibility; custom views can filter by delegate. That supports explicit human ownership and a cross-project view, not a reason to share all channels. [Linear agent docs](https://linear.app/docs/agents-in-linear).
- **Reliability:** The transactional outbox pattern exists to avoid lost messages between two independent writes. Consumers must tolerate duplicate delivery and ordering needs explicit design. Here the committed source outbox post is itself the record, not a second best-effort write after a task mutation. [AWS outbox guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html).

For this office, choose A plus links. One relay and a board directory are simpler to audit than an all-to-all mesh of spawner credentials and retry loops. The core *model session* need not participate in forwarding. Keeping logical destinations independent lets a busy or down repo lag without blocking the rest.

## 4. Concrete proposal

### Board directory and channel layout

- Give each board an immutable deployment key in a small operator-managed directory: `core`, `repo-acme-web`, `repo-acme-api`, `repo-acme-api-release`. Record repo ID, spawner/mail tag, board instance, URL, local port, data path, and enabled routes. A second board for one repo is an explicitly addressed instance, not a second default inbox. Human names are display metadata in this directory, not `BOARD_NAME`.
- Example: core upstream `127.0.0.1:4100`, web `:4101`, API `:4102`, release `:4103`. On the LAN use `https://politburo.local:7440/api/board` etc. via one Caddy process with separate HTTPS listeners, or distinct local DNS hostnames on 443. Keep the internal API mount fixed. Pass the external authority to `--allow-host` and use `--swarm --no-inspect --dir <persistent-dir> --port <upstream-port>`. One system job per board; no `--team-tokens` in this setup. Restrict the core API and board data to its operators and relay identities.
- Repo boards: `intake`, `work/implementation`, `work/review`, `swarm/<tag>/inbox`, `swarm/<tag>/outbox`. Core: `swarm/core/inbox`, `swarm/core/outbox`, `ops/delivery`, `ops/status`. Keep actual structured attention on the local task. Follow the merger's `swarm-message@1` thread-root convention with `swarm.class`, `swarm.urgency`, `swarm.state`; define and version any additions to the routing envelope after checking parity with existing file mail. Do not use the operational inbox as a message log. See `design/swarm-secretaries.md`, `design/swarm-frontend.md`, and the side-session `merger-plan.md`.
- Coworkers post requests to `intake`; the spawner records approve/deny in the thread, and on approval creates a `work/` task linking back. Key the decision and task creation to the source request so a retry cannot make another task. Treat a crash between two writes as incomplete approval and reconcile; never infer approval just because a message says so. Workers claim only `work/` tasks, and get only the channels and actions they need. Use separate grants for humans, spawners, relay and dashboard. No owner credential on a worker or cloud VM.

### A cross-repo request, end to end

1. Web's spawner writes a root in `swarm/web/outbox`, addressed to the default API board and its spawner. Keep the existing `id,class,urgency,from,to,summary,body,at` concepts. Carry immutable origin board/message references, correlation ID, and a bounded body pointer. Resolve routes from trusted configuration and validate the actual board author, permitted class and destination, not just the payload's `from`. An arbitrary post, link, or urgent label cannot authorize running work.
2. The relay tails the source feed from its last durable cursor. In one **relay SQLite transaction**, save the envelope, payload hash, one target row per resolved destination, and the source cursor. Make insertion replay-safe. A single Mac daemon is enough initially. Treat source events and cursors as board-local; continue with `after` and reconcile from the source outbox if a feed breaks. See `packages/board/docs/01-board/05-reading.md`. Keep outbox roots immutable by convention, and do not purge them before all targets are terminal.
3. Post to `swarm/api/inbox` with a deterministic key from source board instance, envelope ID and destination. Pin the relay principal/profile as well as the exact body and channel across retries. Name the relay as author and carry original provenance in the message. A board post key deduplicates retries, not downstream actions; make the secretary's acceptance and approved task creation idempotent too. **Implementation caveat:** `04-messages.md` describes conflicting reuse as `duplicate_id`, but `packages/board/src/server/writes.ts` (`replayOf`) checks author and place and does not compare text/labels. Store and compare the frozen payload hash in the relay; never depend on the board to detect same-place content drift. Prefer the SDK/CLI principal-scoped key format, not guessable raw IDs. Retry the same key after a timeout, even if the destination might already have committed. After confirmation, store the destination post ID and mark *delivered*, not *approved*.
4. API's secretary routes the inbox item by urgency; the spawner accepts, denies, or asks a question locally. A result/ack is a new addressed envelope correlated to the original. The relay ignores inbound copies as sources. Track *queued*, *delivered*, *acknowledged*, and *failed* separately. Retry transient errors with backoff and jitter. Quarantine bad schema, bad routes, and permission failures visibly; requeue with the same key after repair. Do not copy private content into the core delivery log. A body pointer may be inaccessible to the recipient; send a reviewed minimal payload instead of granting broad source access.

**Core broadcast.** Core posts a versioned policy notice to `swarm/core/outbox`. Snapshot its recipients from the directory at acceptance. Create one delivery row per board and mailbox, with one deterministic key per recipient. A down board does not delay other boards. Core sees `n/m delivered` and `n/m acknowledged`; a repo added later gets an explicit catch-up, not a silent change to this broadcast. Keep FIFO only for explicitly ordered streams (for example core policy versions to one recipient); retries or p0 priority may reorder independent work. Use monotone policy versions so obsolete notices cannot undo newer ones. No global order, atomic broadcast, or exactly-once side effects. Dependencies across boards are explicit correlated receipts and local gates, not native `tasks --needs` across databases.

### One jockey view and rollout

Start with a directory page and links to the per-board client views. Then add a jockey-only read model that shows per-board task counts, intake backlog, answers needed, last successful poll, last spawner heartbeat, and relay lag/oldest pending item. Use separate scoped read handles, timeouts, and per-board cursors. A disconnected board is *stale/unavailable*, not zero; never merge its IDs without the board key. Project only necessary fields and assume the dashboard is at least as sensitive as the data it aggregates. In the first version write nothing back from it. Drill down and answer as the verified, allowed responder on the source board. A coworker dashboard would need per-viewer authorization, not the jockey's broad reader.

Pilot with the office LAN and one repo board. Shadow existing file mail; keep one active route per tag and direction during cutover so the two bridges cannot create a loop or duplicate work. Keep a stable sequence/ID mapping for the transition. Add a second board and test cross-repo retries, then move core when parity holds. For remote staff, use Headscale to reach the same TLS API if existing infrastructure and DNS can preserve the canonical URLs; otherwise plan alias-specific joins, or use Cloudflare Access for people if a domain is already available and external processing is acceptable. For cloud workers, expose only job retrieval/lease or result endpoints via a named, Access-protected gateway after provider approval. Give each worker or run a narrow, revocable identity. Do not publish the full API solely for workers. If neither an existing public Headscale endpoint nor an acceptable Cloudflare/domain path exists, keep the system LAN-only; remote/cloud access is not guaranteed at zero incremental cost.

## 5. Mac Studio runbook and acceptance gates

1. **Boot and accounts.** Use system LaunchDaemons in `/Library/LaunchDaemons` with non-admin service users (`UserName`): one per board ideally, separate users for TLS edge, relay, and swarm controller. Root owns the plists and deployed binaries; each service owns its private, durable data/home with restrictive modes. Use absolute paths, working directories, pinned Node and Politburo builds, foreground processes, `--no-open` when using an inspector, and explicit dirs/ports. Use `KeepAlive` and throttling for daemons; use a scheduled job for backups, not an always-restarting backup. A LaunchAgent starts with a user's session and stops at logout; wrong for an always-on backend. `packages/board/src/cli/{inspect,local,serve}.ts` handle SIGTERM and close the inspector, listener, and backend. Allow time for that on planned restarts. [Apple launchd guide](https://developer.apple.com/library/archive/documentation/MacOSX/Conceptual/BPSystemStartup/Chapters/CreatingLaunchdJobs.html), [`launchd.plist` manual](https://keith.github.io/xcode-man-pages/launchd.plist.5.html).
2. **Power and network.** Prefer wired Ethernet, DHCP reservation, UPS for Mac and relevant network gear. On the Mac Studio verify AC settings such as `sudo pmset -c sleep 0 autorestart 1` and inspect effective settings with `pmset -g custom`. Allow display sleep. Test power-loss recovery as well as a warm restart. FileVault preboot unlock can prevent macOS reaching the stage where LaunchDaemons start; do not turn off disk encryption just for uptime. Document the unlock/recovery procedure and test this exact hardware/OS; unattended FileVault cold boot is **unverified** here. If testing Tailscale on the Mac, select a variant that supports running before login; its macOS docs describe the open-source daemon for unattended installs. [`pmset` manual](https://keith.github.io/xcode-man-pages/pmset.1.html), [`fdesetup` manual](https://keith.github.io/xcode-man-pages/fdesetup.8.html), [Tailscale macOS variants](https://tailscale.com/docs/concepts/macos-variants).
3. **Consistent backups.** Each board uses WAL and keeps attachment files beside the DB (`packages/board/src/store/sqlite.ts`, `packages/board/src/server/{local,blob}.ts`). Use SQLite's online backup API (e.g. SQLite CLI `.backup`) or `VACUUM INTO` a new file for a live DB snapshot. Use bounded busy retries and monitor size/free space. A passive WAL checkpoint can help monitor/checkpoint the writer; long readers may delay progress. A checkpoint by itself is not a backup, and copying only the live `.db` can omit committed WAL data. For a consistent restore bundle, briefly quiesce uploads, posting and workers during the DB+attachments capture, or snapshot the database and verify that every referenced blob exists in the staged copy before publishing it. Include relay DB/cursors, deployment manifest and needed durable runtime files. Recover access configuration separately under encryption and restricted ownership. Store encrypted copies on an independent disk or existing NAS; keep an offline copy. Start with nightly and pre-upgrade snapshots (nightly implies up to a day's loss), and rehearse `PRAGMA integrity_check`, attachment reads and relay replay on an isolated restore. Take a coordinated checkpoint or reconcile restored boards and relay state before enabling writes. After a point-in-time restore, don't blindly replay external effects or previously approved jobs. [SQLite online backup](https://www.sqlite.org/backup.html), [`VACUUM INTO`](https://www.sqlite.org/lang_vacuum.html), [WAL and checkpoints](https://www.sqlite.org/wal.html).
4. **Logs and updates.** Separate bounded service logs; record board ID, envelope ID, latency, result and reason class, not bodies or auth headers. Set per-file size/retention limits and ensure the service reopens logs on rotation, or use a log sink that rotates itself. `StandardOutPath`/`StandardErrorPath` capture output; don't assume rename alone changes an open descriptor. Pin releases, canary a replica on a different port with restored data, back up, then restart one board at a time. Retain the prior build and compatible snapshot; do not assume an in-place downgrade after a storage change. `local()` pending scheduler timers can be lost on restart (`packages/board/docs/01-board/10-local.md`); keep critical deliveries and review deadlines as durable jobs with startup reconciliation. [launchd plist manual](https://keith.github.io/xcode-man-pages/launchd.plist.5.html), [`newsyslog.conf` manual](https://keith.github.io/xcode-man-pages/newsyslog.conf.5.html).
5. **Health and laptop independence.** Probe local discovery and an authenticated read through the office TLS URL. Check auth rejects, per-board stale feeds, TLS expiry, disk/WAL growth, queue age, dead letters, last successful backup, and spawner/worker heartbeats. `KeepAlive` restarts a dead process; it does not prove a wedged listener or a stuck relay is healthy. Use a separate health job and, if possible, a second always-on LAN observer. Put core routing, secretary wake loops, spawner launch/resume and reconciliation on the Studio or supported always-on workers; don't leave scripts in laptop scratchpads or `/private/tmp`. Test the headless model launch/auth path under the service account: if an interactive dependency remains, show it as unavailable and preserve pending work, rather than reporting the whole swarm healthy. Laptops are clients only. A sleeping client may lose its inspector window; it must not stop job leases, mail or delivery.

**Go-live gates:** test one human intake → spawner deny/approve → worker claim on the pilot; show intake users cannot create, adopt, or claim tasks in work channels, alter grants, or answer as the owner. Verify person attribution and join persistence across restart at the exact TLS URL. Test reply correlation, board outage during broadcast, relay kill after destination commit before receipt, repeat approval, and stale/dead-letter display. Disconnect a laptop, reboot the Studio without GUI login, and restore a board plus its attachments and relay records. Do not cut over core until those checks pass. The major residual risks are the single Mac/disk/network failure domain, grant or proxy mistakes, lost pending timers, and hosted VM networking limits. Backups reduce data loss, not downtime; a spare restoration target and a named recovery owner are more valuable than adding a second frontend.
