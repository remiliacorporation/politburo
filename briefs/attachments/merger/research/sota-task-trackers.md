# Task trackers for one Politburo board per repo

## Executive summary

Use the board to run the swarm, not to run a second copy of the backlog. In Remilia World, beads remain the work record. In repos that use Linear or GitHub Issues, that tracker remains the work record. Repos with no tracker use native board tasks. In all modes, the board owns dispatch, leases, attempts, evidence, and requests for human attention. “Swarm finished” and “issue closed” are different facts.

Ranked recommendations:

1. **Choose one authority per repo, not a sync direction per issue.** Default new repos to `board`; onboard existing repos in `beads`, `linear`, or `github` mode. In external modes show a live or cached queue and create a linked board task only when the swarm accepts work. Remilia World's existing GitHub mirror does not become another intake source.
2. **Put the adapter and reconciliation loop on the Mac Studio.** Use one writer per repo and keep the office board private. Give cloud mobs a bounded work brief. Collect their results via the existing session transport or independently observed Git/PR evidence, subject to repo policy. Do not give each mob tracker credentials or make the secretary a human re-keying step.
3. **Start with a read-only Remilia World shadow and native board mode.** Compare readiness and coverage, then enable selected dispatch after verifying how claims will be shared with Charlie's workers. Put any Dolt publication behind the existing named-approval gate. Do not start by turning on bidirectional message sync.
4. **Add GitHub and Linear as scoped API adapters.** Start with incremental polling where there is no webhook ingress. Add authenticated webhook ingress if needed and keep periodic reconcile. Enable outbound comments and transitions separately and only for repos that want them. No Connect, paid relay, GitHub Actions, or external coding-agent subscription is needed for this design.

## 1. Beads: what ships and what Remilia World does

### Upstream and the installed version

The local Homebrew binary says `bd 1.3.4`; the public latest release endpoint returned the same version, dated November 4, 2026 ([release](https://github.com/gastownhall/beads/releases/tag/v1.3.4)). Version matters. Steve Yegge's [October 2025 introduction](https://yegge.ai/essays/introducing-beads-a-coding-agent-memory-system/) explains the original idea: preserve discovered work and dependencies across coding sessions. The [v0.20.1 README](https://github.com/steveyegge/beads/blob/v0.20.1/README.md) describes the old SQLite, Git-tracked JSONL, and sync daemon. That is not the present storage model. Yegge discusses why he would have used Dolt earlier in [Software Survival 3.0](https://yegge.ai/essays/software-survival-30/). For the design and motivations rather than current CLI semantics, see his [AI Tinkerers conversation](https://one-shot.aitinkerers.org/p/steve-yegge-on-agentic-coding-beads-and-the-future-of-ai-workflows) and [Software Engineering Daily discussion, February 2026](https://softwareengineeringdaily.com/podcasts/gas-town-beads-and-the-rise-of-agentic-development-with-steve-yegge/).

- **Record.** A bead is a typed issue with a title, description, design, acceptance criteria, notes, status, P0–P4 priority (P0 highest), assignee, timestamps, close reason, labels, metadata and optional external reference. Comments and typed graph edges are distinct from the issue body. The local help and versioned [types](https://github.com/gastownhall/beads/blob/v1.3.4/internal/types/types.go) distinguish `open`, `in_progress`, `blocked`, `deferred`, `closed`, `pinned`, `hooked`, and configured custom status categories. Typical types are task, bug, feature, epic and chore. Roots use a project prefix plus a short hash-like ID; children can have numbered suffixes, e.g. `rw-4u5.41.29`. Use explicit parent edges, not string parsing, for hierarchy; IDs may be renamed and issues reparented. Scope identities to the configured store, not just the `rw-` prefix. [Issue model](https://github.com/gastownhall/beads/blob/v1.3.4/docs/core-concepts/issues.md), [IDs](https://github.com/gastownhall/beads/blob/v1.3.4/docs/core-concepts/hash-ids.md).
- **Readiness.** Local `bd ready --help` says it filters open work with no active blockers and excludes in-progress, blocked, deferred and hooked work by default; it offers `--parent`, `--explain`, `--unassigned` and optional atomic `--claim`. `bd update ID --claim` sets assignee and `in_progress` atomically in the same store and is idempotent for the current owner. `update` also has `--if-status` and `--if-assignee` for guarded writes, separate from `--claim`. `heartbeat`, `unclaim` and `reclaim` are present. Local claim atomicity does not protect independently cloned replicas. For a shared queue, use a shared store, and also align the team's handoff policy. [Coordination](https://github.com/gastownhall/beads/blob/v1.3.4/docs/multi-agent/coordination.md), [backend caveats](https://github.com/gastownhall/beads/blob/v1.3.4/README.md).
- **Edges.** `blocks` is a hard prerequisite; `bd dep add A B` means A depends on B. `parent-child` is structural but can propagate a parent's blockedness; it does not mean the child waits for the parent to be completed. The short issue overview calls it non-blocking; the detailed dependency doc and the [parent-cascade issue](https://github.com/gastownhall/beads/issues/6506) qualify that. `conditional-blocks` and `waits-for` can affect readiness; `related`/`relates-to`, `tracks`, `discovered-from`, `caused-by`, `validates`, and `supersedes` are annotations, not ordinary prerequisites. The local `dep add` flag lists a subset and additional names such as `until`; do not treat the help list as a complete semantic schema. Gates can wait for PR merge, successful CI, time, another bead, or a human. There are external capability refs, too. Keep the provider's readiness computation rather than rebuilding this graph in board `needs`. [Dependencies and gates](https://github.com/gastownhall/beads/blob/v1.3.4/docs/core-concepts/dependencies.md), [graph links](https://github.com/gastownhall/beads/blob/v1.3.4/docs/core-concepts/graph-links.md).
- **Storage and sync today.** Embedded Dolt is in-process, single-writer/file-locked, under `.beads/embeddeddolt/`. The optional SQL-server modes support concurrent processes; worktrees of the same checkout normally resolve to the same store, unlike independent clones. `bd --help` has no old `daemon` command. `bd dolt start/stop` are SQL-server lifecycle controls, not the old JSONL daemon; `bd serve` is a separate loopback API. Dolt commits are distinct from code commits. A Git-backed Dolt remote uses `refs/dolt/data` at Git `origin`, separate from source branch history; other Dolt remote transports exist. A cloud `git clone` alone is therefore not a bead database. A fresh clone needs a compatible `bd` and bootstrap or an existing provisioned store, permission to read the remote, and an explicitly allowed write route if it will publish. `issues.jsonl` is now export/interchange or a legacy bootstrap path, not the standard sync record; import upserts and cannot propagate deletions by absence. Old hooks/documentation about JSONL do not change that. [Dolt architecture](https://github.com/gastownhall/beads/blob/v1.3.4/docs/architecture/dolt.md), [sync concepts](https://github.com/gastownhall/beads/blob/v1.3.4/docs/core-concepts/sync-concepts.md), [proxied server design](https://www.dolthub.com/blog/2026-07-22-introducing-beads-proxied-server-mode/).
- **Merges and failures.** The installed `bd sync --help` describes pull → positive conflict check → recompute denormalized `is_blocked` → push, with bounded retries for a push race or busy working set. Some conflicts are auto-settled (including selected issue cells by last write); the rest halt, not force-push. Exit 2 is conflict, 3 is transient retries exhausted, 4 is a stuck dirty working set; 1 is a general error. This is not `bd federation sync`. A Dolt merge is not a distributed lock. Treat a stale graph, an unavailable store, or schema mismatch as “not safe to dispatch,” not “nothing to do.” Pin versions on writers. The 1.3.4 release warns against `bd compact`/`flatten` on affected migration-0062 clones; the [incident report](https://blog.gascity.com/posts/beads-1-2-1-incident-report/) and [issue #7039](https://github.com/gastownhall/beads/issues/7039) document audit-history problems. [Sync command source](https://github.com/gastownhall/beads/blob/v1.3.4/cmd/bd/sync.go), [release warnings](https://github.com/gastownhall/beads/releases/tag/v1.3.4).
- **Multi-repo and mail.** `bd repo` supports primary/additional repo hydration (the documented `bd repo sync` route reads additional repos' JSONL exports), and routing can send personal/contributor work to a separate store. Federation is a separate peer feature. Beads supports handoffs through comments, labels, claims, formulas/molecules, gates and merge slots. `bd mail` delegates to an outside provider such as `gt mail`; it is not an inbox transport to use instead of Tigeryard mail. Gas Town uses Beads for its own orchestration and messaging, not a feature available from every bare `bd` install. Installed `bd github` and `bd linear` also have issue-sync commands; they are optional import/export, not runtime claim or publication policy. [Routing](https://github.com/gastownhall/beads/blob/v1.3.4/docs/multi-agent/routing.md), [federation](https://github.com/gastownhall/beads/blob/v1.3.4/docs/multi-agent/federation.md), [mail implementation](https://github.com/gastownhall/beads/blob/v1.3.4/cmd/bd/mail.go), [GitHub sync notes](https://github.com/gastownhall/beads/blob/v1.3.4/README.md#-github-issues-sync), [Gas Town author's account](https://yegge.ai/essays/welcome-to-gas-town/).

### Remilia World: local evidence and operating rules

Local `.beads/` contains `config.yaml`, `metadata.json`, `.local_version`, `.gitignore`, `embeddeddolt/`, `backup/` (Dolt archives and manifest), lock files and `last-touched`. No `.beads` files are tracked in the code checkout; no `issues.jsonl` was present. Selected non-secret metadata identifies embedded Dolt; `no-push: true` is set. The coordinator notes record the contributor Git role and initial migrations. A narrow Dolt SELECT with filesystem writes and network denied did not start: the CLI tried to initialize global config. I did not relax the restriction. Samples below are from the repo's locally available `origin/master:docs/pickup.md` and the named notes, not a live database dump. Their current DB status is **unverified**.

**Pick and close.** `CLAUDE.md` points to `AGENTS.md`. Charlie's rules say file work and deferred defects in beads before writing code; put subtasks under an epic; take P0/P1 first; read the parent; spend up to five minutes checking `origin/master` and search branches/PRs (including drafts) before claiming. Use a distinct `--actor` because agent Git identities can be shared. The agent/person doing the work can close it with the merged PR and SHA, or close already-done work with a commit citation. Append notes; do not overwrite them. In observed cloud work the coordinator made local claims, received evidence from mobs/sprites and performed local closures; the VM was documented as having no `bd`, so the bead text was embedded in briefs. Do not require Charlie to type routine closures. Do not let a mob or script infer a closure from “patch ready” or “PR opened.”

**Publish and approve.** `bd-pushed` in `HANDOFF-INDEX.md` refers to successfully publishing the Dolt history containing the change to `origin`'s `refs/dolt/data`. It does not mean a local `bd close`, a code branch push, a PR merge, or a GitHub mirror update. Example: the notes report `de8f535a → 6a8004c3` for a named publication including 30+ closures and 13 migrations; they also report locally closed but not bd-pushed beads. The coordinator's standing rule requires bonklek's own yes naming the bead push, with `no-push` off only for that push and restored afterwards. Code push, opening a PR, merge, tag and release are separate outward actions under the repo's named-approval rules; one approval does not authorize the others. The notes also record delegated periods of PR-focused work. Use current grants, not historic approvals. Changed fixture hashes or defaults, weaker checks or removed tests, new dependencies, rule/constitution changes, and frozen upstream or cross-repo work go to the operator according to the repo rules. Backlog/notes give concrete holds for new names, GPU/blind-eval/Studio evidence and tooling adoption. Follow current check and review policy: the locally recorded `origin/master` calls for head-bound `quick-ok`, a serialized landing check, and model/person review on an explicit trigger. The older checked-out `AGENTS.md` called for fresh review on every PR. The locally recorded `origin/master` itself contains both a no-auto-merge rule and an older quick-start auto-merge instruction; do not infer permission to automate merge. Coordinator notes say not to depend on Actions billing; collect local evidence and surface missing required receipts, not a green substitute.

**Existing GitHub mirror.** `AGENTS.md` makes this repo's GitHub Issues the only external-tracker exception. `.githooks/pre-push` starts `scripts/gh-sync.sh` in the background; it can also run by hand. It serializes per Git common dir, pushes changed/unsynced open beads first, checks for concurrent edits, then pulls GitHub changes into local beads. It paces writes (one per five seconds), stops on 403 and leaves a stop file; it excludes beads linked to other repos. The script documents a real race (`rw-dtu.15.1`): pulling first reopened a newer local closure, so the intended precedence is bead wins when both sides changed. This is not a transactional or independent sync authority, and it is not the Dolt publish step. Do not add another issue importer or writer for this repo. `docs/engineering.md` also documents dedupe of survivor beads by stable finding identity and a team Studio worker that does not itself file beads.

**Observed wrinkles.** Status lags code (dozens of documented “already done” closures). The coordinator recorded an empty `bd ready --parent rw-4u5.41` because the children appeared blocked by their own parent; the pickup doc still listed them. Upstream [#6506](https://github.com/gastownhall/beads/issues/6506) and the [main changelog](https://github.com/gastownhall/beads/blob/main/CHANGELOG.md) describe a fix for that class; that does not establish the graph is fixed locally on 1.3.4. Show `ready` disagreements and actual edges. Do not silently dispatch blocked work or rewrite an epic to make work appear. Sources: the three requested Remilia notes, `HANDOFF-INDEX.md`, `AGENTS.md` (checkout and cached `origin/master`), `CLAUDE.md`, `docs/pickup.md`, `docs/engineering.md`, hook and mirror script. No remote fetch or write was performed for the local evidence.

## 2. Linear and GitHub: API needs and existing Politburo behavior

### Linear

Scope one installation to a configured team/project plus opt-in rule (label or state IDs); route a team shared by repos using an explicit project/repo rule. Read issue UUID, display ID, URL, revision evidence, workflow state ID/type, issue fields, parent/relations, assignee and comment IDs. Use GraphQL cursor pagination, `updatedAt` filtering with overlap, and direct reads of active issues. Comments and state changes are separate operations. Use workspace-approved OAuth app actor for durable integration and attributable comments; a restricted personal API key is enough for a single-workspace read pilot if team policy permits. Request `comments:create` only when enabled; issue update needs write rights. App-agent delegation is separate from the human assignee and from Politburo leases. Agent Sessions are optional UI, not a prerequisite. [GraphQL](https://linear.app/developers/graphql), [filtering](https://linear.app/developers/filtering), [pagination](https://linear.app/developers/pagination), [OAuth](https://linear.app/developers/oauth-2-0-authentication), [assignment and delegation](https://linear.app/docs/assigning-issues), [agent API](https://linear.app/developers/agents).

Linear prefers webhooks: signed HTTPS endpoint, verify raw body and timestamp, dedupe deliveries, and enqueue then acknowledge. Missed events still need reconcile. For an office-only board use low-frequency scoped polls, not full workspace scans. Hydrate comments, dependencies and exact state on selection or in reconciliation; do not assume every comment or relation change advances the issue's clock. Linear documents 2,500 requests/hour per API-key user and 5,000/hour for OAuth at standard limits, separate complexity and operation limits, and a max single-query complexity of 10,000. Read headers/errors, cap nested queries and back off. Pricing lists API/webhook access on Free, with 250 issues and two teams and higher limits on some paid plans. The adapter requires no upgrade for a Free workspace within its limits or a team already using Linear. Do not promise unlimited free capacity, paid triage rules, or an extra seat. [Webhooks](https://linear.app/developers/webhooks), [rate limits](https://linear.app/developers/rate-limiting), [pricing](https://linear.app/pricing), [triage rules](https://linear.app/docs/assigning-issues).

### GitHub Issues

Use the repository issues endpoint for intake and reconcile with `state=all`, `since`, pagination and overlap; explicitly exclude responses with `pull_request`. Key by platform host and stable issue identity, with repo identity in scope and the issue number and URL for display. Read labels, state/reason and all assignees; use separate comment and relationship endpoints as needed. Watch `issues` and `issue_comment`; PRs are evidence on a separate stream. Read native issue dependency/sub-issue edges, not issue-body checkboxes or Project status by default. Start with a repo-scoped GitHub App installation with Issues read, add Issues write only when needed, and add PR read for evidence if needed. App installation credentials are short-lived (one hour). Fine-grained user access is a pilot fallback, not the default identity. [Issues](https://docs.github.com/en/rest/issues/issues), [comments](https://docs.github.com/en/rest/issues/comments), [assignees](https://docs.github.com/en/rest/issues/assignees), [dependencies](https://docs.github.com/en/rest/issues/issue-dependencies), [sub-issues](https://docs.github.com/en/rest/issues/sub-issues), [App auth](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

With webhooks verify signatures, dedupe by `X-GitHub-Delivery`, answer quickly after durable enqueue, and reconcile or redeliver missed events. Without ingress, use conditional requests when supported and a slow full sweep; a correctly authenticated 304 need not consume primary quota. The primary limit is normally at least 5,000 requests/hour per App installation (60/hour unauthenticated); secondary limits still apply, including on bursts of writes. Serialize writes, honor retry/reset data and stop on auth/permission faults instead of assuming every 403 is throttle. Issue APIs work against an enabled repo on the team's existing GitHub account, including Free; no runner, Marketplace purchase, Copilot license or Project automation is needed. Beware of automatic closure from PR keywords on merge; don't generate `Fixes`/`Closes` when closure belongs to a separate gate or another tracker. [Webhook guidance](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks), [REST limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), [REST guidance](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api), [pricing](https://github.com/pricing), [PR/issue linking](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue).

### What is already implemented in the fork

Checked Politburo `b146e75b`, `packages/board/src/sync/{engine,fn,provider,state,slack,github,linear}.ts`, `packages/board/docs/02-sync/{01-overview,03-slack,04-github,07-linear}.md`, `03-guides/09-self-host.md`, `01-board/11-tasks.md`, and `SPEC.md` (Sync, Local, Tasks and sync). These are **thread connectors**, not task tracker adapters.

| Connector | What it does in a configured host | What it does not do |
|---|---|---|
| Slack | Channel mapping; mirrored posts/replies, edits/deletes, reactions, mentions by ID, files subject to permissions/limits, optional typing and source reads. An outbound root can start a Slack thread. | No issue lifecycle, task claim or structured approval. Slack posting can duplicate if accepted before receipt is recorded. |
| GitHub | Per-repo mapping by issues and/or PRs. Imports lifecycle, comment changes, PR reviews/inline comments, relevant CI workflow status, state/tag/assignee labels, and title edits; a comment can hydrate a missing root. | The default repo mapping uses `into`: no outbound writes. A custom function or `mirror` can send discussion to an existing issue/PR; there is no outbound issue creation/start, issue state/assignment mutation, dependency sync or board-task transition. Description-only issue edits don't update the root. Do not mirror private board/Slack discussion into a public repo. |
| Linear | Per-team mapping; issue root with URL and property labels, comments including nested reply/edit/delete paths, inbound state and property labels. Can read project/team/issue on demand. In a mirrored channel a board root creates a Linear issue, and an edit of that board-owned root updates its description. Linear edits affect Linear-owned roots. | Not a backlog scanner: older issues generally import on human edit/comment, and automations/archiving alone do not backfill. A team move can create a new board thread because the sync target includes team key even though issue UUID stays stable. Deleting a board root doesn't close the issue; no task, assignment, dependency, or issue-status writeback. Reaction support is limited (outbound creation on comments only, not removals or inbound). |

`board({sync: …})` supplies the routes. Connect is optional: a connector name requires Vercel Connect's app credentials/short-lived minting and OIDC trigger forwarding for the target deployment. Without it, configure a Chat SDK adapter with platform credentials and signing verification. Slack needs a bot app with Events API subscriptions/scopes; GitHub needs an installed App with the selected topics and permissions (the full connector documents Issues and PR read/write plus Actions read); Linear documents an app actor with read/write, issue/comment creation scopes, and Issue/Comment webhooks. Each platform must be able to deliver to `/webhooks/<key>` under the configured mount. There is no documented polling fallback for this built-in sync. The engine persists inbound event IDs, lanes and copies/receipts, and suppresses same-source echo. Creates/posts have bounded retries; not all ops are retried and provider acceptance may precede the durable receipt. Board labels do not round-trip as platform issue fields.

**`vb serve` as shipped does not run these connectors.** `src/cli/serve.ts:serveLocal` creates `local()` and passes no `sync` or `watch` config to `board()`. The self-host guide is explicit. The underlying `local()` backend can run configured sync in a custom long-lived Node process; no hosted board or connector service is inherently required. Another design is a separate Studio worker talking through the served board API. Do not point a webhook at vanilla `vb serve` and expect configured ingress. `SPEC.md` also distinguishes Vercel's bare hosted backend from a deployment that runs `board()` with sync elsewhere. A board task can travel as a thread, but inbound replies are not claims, task transitions or structured approval answers. The spec mentions rendering task state, but the current task docs/engine and later spec note say `task.*` does not trigger re-render of copies. Build against current behavior.

## 4. Options

| Option | What a board-disconnected cloud mob does | Conflict rule and what breaks |
|---|---|---|
| **(a) Board is the live task; all trackers import/mirror.** | Reads a dispatch snapshot and returns an attempt result through the spawner or an allowed Git/PR path. Tracker reads are context only. Direct mob edits, including `bd` writes, would have to be commands to the board rather than authoritative updates. | Board must win writes; import can only be an explicit request. Breaks Remilia's bead-first and `bd ready` workflows, encourages drift and second editing surfaces, and makes cloud tracking stale during board outages. Good as pure board mode, poor as a universal mirror. |
| **(b) Tracker owns work; board links in-flight runs.** | Reads a dispatch brief. Where allowed it can also read a bootstrapped bead store, Linear, or GitHub itself; otherwise the Studio supplies source context and refreshes it. Mob writes findings/patch/PR evidence through approved paths. Outward tracker mutations go through the local adapter (or another explicitly chosen single writer); an offline bead replica is not a shared claim queue. | Tracker wins issue fields; board wins execution. External cancellation/change can invalidate a run but not rewrite its historical evidence. A network/store outage halts new eligibility; work can be prepared offline without releasing gates. Does not solve repos with no tracker unless a board adapter is offered. |
| **(c) Per-repo authority: board-native or (b). Recommended.** | Same brief across all modes. Native mode reads no external task record; returns board run evidence indirectly. External mode can read the native source if authorized; no unmediated issue writes by default. | Per-field ownership stays simple; one configuration and one active dispatcher per repo. Costs are validation, safe operator-driven cutover, and preventing a mirror from being ingested twice. Do not support hot changes of authority: drain attempts/outbox, preserve aliases and links, then activate the new scope. |

The Mac worker and spawner handle ordinary routing. The secretary can keep the small mail envelope and route typed results without choosing tracker precedence. Colleagues submit via the native tracker or a board **submit-to-tracker** form. A form shows pending/failed until the tracker acknowledges creation; it must not invent a second editable issue. Native mode submits directly to a board task.

## 5. Concrete interface and first slice

Keep the adapter in `packages/swarm`, not in the board event reducer. Reuse board tasks and grants on Studio. Use a local launchd worker and durable cursor, link, inbox and outbox tables. Board run threads use `noSync`; the published comment is an explicit allowlisted summary, never a transcript.


### Conflict, replay, and office/cloud handoff

1. Enforce one active run reservation for `(repo, canonical ref)` transactionally on the Studio. Reserve before launching; use stable run and launch IDs and a deterministic board task-create idempotency key. A database uniqueness constraint plus an outbox is not exactly-once cloud execution: on ambiguous launch, recover by launch ID/session lookup, or mark unknown and pause rather than starting a twin. Recover partial local board/source claims from receipts. A board lease is scoped to the swarm; external editors or independent runners do not obey it. For Remilia, use the same bead store and claim atomicity with any other picker, or an explicitly delegated subset Charlie's workers agree not to pick. If they use independent replicas and unpublished claims, show that dedupe is Studio-only and keep autopick off.
2. Inbound delivery dedupe and issue dedupe are different. Persist event IDs before ack; reconcile current records per canonical ref. Poll with a bounded overlapping high-water window, stable pagination/tie handling and active-issue refresh. Don't advance a cursor past uncommitted data or treat a 404/403 as proven deletion. Keep old aliases for moved/renamed work after verification. If scope, blockers, assignee or brief semantics changed, recompute eligibility; park new dispatch or flag an active attempt for rebrief. A label-only update should not spawn another run. Stale completions are recorded for audit, not allowed to change issue or task state.
3. Cloud reads an immutable brief with ref, bounded text, base SHA, expected outcome/checks and attempt ID, no reusable authority. Existing local spawner/transport collects its report when possible. A Git watcher can independently read an approved branch head, PR, check, or merge; restrict to expected repo/branch/head and correlate to lease generation. A local-only artifact cannot be recovered by a Git watcher; use the existing session report/retrieval path if available, or show it as missing. Do not push merely to get a heartbeat. Tracker text is untrusted data; it cannot issue a command, confer authority, or approve a release.
4. Tracker wins for title, scope, issue workflow, assignment and dependencies. Board wins for leases, park/attention and attempt history. A code change only counts when the policy's proof for the expected head/base is verified. Canceling/withdrawing an issue stops new dispatch and fences future outward changes; preserve prior evidence. No whole-record last-write-wins across systems. Each outward mutation queues a unique operation ID; re-read exact allowed fields, validate lease/policy/approval and head, and store remote ID or classify conflict. Idempotent field setters can converge by readback; comments/creates can have ambiguous acceptance. Use provider idempotency where proven; otherwise add a safe operation marker where supported and search the target before retrying. If the outcome cannot be established, do not blindly create a second object. Suppress self-echo by recording origin and receipt IDs, not by ignoring all app-authored external changes.
5. Keep technical and human gates separate. Retry transient reads and sends with backoff and a cap. Raise one structured attention item per unresolved real decision (e.g., Dolt merge conflict, fixture change, named publication), keyed to the proposal and evidence SHA. Dedupe notifications and invalidate approval if its subject/head changes. For Remilia maintain separate `locally_closed`, `publication_pending`, `bd_pushed` and optional mirror-observed indicators. A Dolt push may include unrelated migrations or pending edits: review exactly what the approved batch would publish; if that cannot be isolated, stop. No one must approve routine reads, briefs, duplicate detection or progress reconciliation.

### Minimal first slice

- Add `board` and `beads` modes and a `scan/get` adapter. For Remilia pin `bd` and test runtime invocations against a fixture first, then use an authorized store without auto-push, automatic migrations, `bd sync`, GitHub issue sync or a webhook. Shadow a small allowlist (e.g. one epic). Show the sampled queue, source age, current refs and why a bead is not runnable, including the parent-gate mismatch and already-done work. Don't create tasks for the backlog. If operating on embedded Dolt, serialize calls and verify initialization/side effects before claiming the observer is read-only.
- Add a manually selected but automatically executed dispatch on a test repo or delegated Remilia subset: Studio reserves one run and its board lease; spawner sends a brief; result arrives via the existing transport or allowed PR/branch observation. No code push, PR or closure is implied by selecting a task. Run a native board-only example too. Enable automatic selection only after overlap and shared-claim checks pass. Next add coordinator-only guarded bead closure with evidence; leave remote publication and mirror behavior as-is until explicitly approved.
- Acceptance: two simultaneous dispatch requests make one run; a crash after claim/before launch and a replayed result create no second attempt; a late result after lease expiry only logs evidence; a disappeared or reparented blocker, external close/reopen, or unreachable store cannot silently turn into readiness; an authorized local closure remains visibly unpublished until the named push is verified; a GitHub mirror issue cannot dispatch the same bead. Disabling the worker leaves the canonical tracker and existing workflows intact. Match the merger plan's shadow-first cutover and its initial no-cloud-ingress choice (Q3).
- Then implement GitHub issue intake and Linear intake with the same contract, initially read-only. Test page ties, dropped/duplicate deliveries, edits during a run, permission loss, and app/service outages. Enable milestone comments before any state mutation; adopt signed webhooks only where needed for latency. That sequence provides a usable free/self-hosted path without first building all four write paths.
